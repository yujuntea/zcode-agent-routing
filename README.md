# zcode-agent-routing

[English](README.en.md) | **中文**

把「这次该派哪个模型」从人的临场判断，变成写在配置里的规则。

一套跑在 [ZCode](https://zcode.ai) 上的多智能体路由：主会话负责想和裁决，便宜的模型负责干活，
两个**不同家族**的模型自动轮换做一审，最后一层终审保证和上游都不同源。

配套三个 hook，做三件事：**换人、拦跳步、修配置**。

---

## 它解决什么

多智能体的难点不在「能派几个角色」，而在**每次该派谁**。人工决定有三个具体毛病：

**一、凭直觉派。** 什么时候该上贵的模型，全凭当下心情。手上活一多，
「这个改动值不值得上强模型」「这次审查是不是可以省了」，判断就退化成直觉。

**二、同一个任务只被一种视角看过。** 审查者和干活的是同一个模型时，
它觉得没问题的代码，往往正是它自己会写出来的代码——**它看到的是同一套盲区**。

**三、跳步没人发现。** 上一环说好下一环该谁审，派的时候随手换了个环节，
链条看着还完整。这类失效**不报错**，是整套流程里最阴险的一种。

这个项目把这三件事分别交给：配置文件、轮换 hook、闸门 hook。

---

## 结构:四层

| 层 | 角色 | 干什么 | 模型怎么挑 |
|---|---|---|---|
| 指挥层 | 主会话 | 规划、拆分、裁决、编排 | 主力那个 |
| 执行层 | `impl-worker` | 按规格写码、跑命令、批量改文件 | **两个快模型按需切** |
| | `vision-reader` | 判图、页面比对、录屏转写 | 有视觉输入的 |
| | `doc-writer` | 中文成稿、润色 | 中文好的 |
| 一审层 | `first-reviewer-a` | 独立第一审 | 强模型 |
| | `first-reviewer-b` | 独立第一审 | **和 A 不同家族** |
| 终审层 | `reviewer` | 异构终审 | **和产出方、A 都不同家族** |

本仓库带的示例配置：

- 一审 A = **GLM-5.4**（长思考在审查位上是收益，见下）
- 一审 B = **DeepSeek-V4.1-Flash**
- 终审 = **Kimi K3.1-Pro**（另一侧可换成任意外部模型，按案轮换）
- 执行层 = **GLM-5.3-Flash** ⟷ **MiniMax-M3.1-Flash** 按需切

## 一个反直觉的结论:一审不保证异构,终审才保证

把每层和「跟主会话是不是同源」摆在一起看，设计意图就显形了：

| 层 | 与主会话的关系 |
|---|---|
| 执行层 | 不同源 |
| 一审层 | **两个成员里必有一个与主会话同家族**（主会话用 DeepSeek 时，B 成员也是 DeepSeek） |
| 终审层 | **对上游全部异构**——不管主会话切到了哪个模型 |

所以：

- **一审层保证的是「两个独立视角」，不保证「异构」。**
  它补的是独立性、对抗性、没有写作记忆的偏袒——但同类模型共享的盲区，它看不见。
- **终审层保证的是「异构」。** 它的候选模型和上游任何一个都不同源，
  所以**不管主会话当时切到了哪个模型，终审这一层始终是异构的**。

**终审买的不是「更强」，是「保证不同源」。**

这还顺带解决一个疑问：主会话临时切到强模型当指挥，它又去当审查员，审查不就在审自己了吗？
—— 不会污染，因为异构性由终审层兜底，不依赖主会话用谁。

## 三个 hook

| Hook | 事件 | 解决什么 |
|---|---|---|
| `hooks/review_role_rotation.py` | PreToolUse | 同一个会话内，两个一审成员**自动交替**；顺手把审查设成后台，不阻塞主会话 |
| `hooks/review_dispatch_guard.py` | PreToolUse + PostToolUse/Failure | 派审查角色必须带**进场依据**（上一份报告的下一跳状态行，或「首审」声明），缺了就拒 |
| `hooks/heal_frontmatter.py` | SessionStart | 面板保存会静默丢字段（`memory`、`thoughtLevel`），会话启动时幂等补齐 |

三个都遵守同一条纪律：**绝不因为自己出错而卡住流程**。

- 轮换 hook 只改写派发，永不 deny；
- 闸门只在「缺进场依据」时拒绝，载荷残缺或自身异常一律放行（fail-open）；
- 自愈 hook 自身异常只记日志，退出码 0。

### 轮换是怎么分派的

```
第 1 次派 first-reviewer-a → 实际落到 first-reviewer-b
第 2 次派 first-reviewer-b → 实际落到 first-reviewer-a
```

同一个会话内交替，新会话的起始成员按全局 parity 交替（避免所有会话都从同一个成员起步）。
`prompt` 里写 `REVIEW-ROLE-FIXED` 可以固定本次成员（仅当次，别写进任务书模板）。

### 闸门认什么依据

派审查角色时，`prompt` 或 `description` 里必须能读到下面之一：

- 一行以 **`〔下一跳`** 开头（最常见）；
- 一行以 **`〔状态`** 或 **`〔本轮状态`** 开头（真实写法里常见「状态在前、下一跳在后」）；
- 一行以 **`首审`** 或 **`状态：`** 开头（链中第一环，没有上一环，如实声明）。

前缀允许 `>`、`-`、`#`、反引号、`**`，也允许一个 **ASCII 角色标签**（如 `K3：〔下一跳…〕`、`glm：首审…`）——
中文散文句不算（所以「这里写一个检查清单：〔下一跳…〕」蒙混不过去）。

**关键：判定是「以标记开头」，不是「包含标记」。** 这条是拿真实任务书校准出来的：
早先按「包含」判定时，一行 `状态行格式是〔下一跳:X〕` 的格式说明就能骗过闸门，
而闸门本来就是为了拦模板复用——自己被模板骗了就没意义了。
收紧时用 889 份真实任务书做了 A/B 回归，确认同时还要认
`〔状态` 开头、反引号包裹、`> ##` 引用块标题、`（逐字）` 这类标题后缀、
以及未闭合代码块之后的内容，最终**零回归**。

**`prompt` 内联路径的判定略宽：出现完整标记即算**（不看是否开头）。这是有意的——
内联文本是你当下手写的，任务书才是会被反复复制、最容易残留模板的地方，收紧主要收在那里。
所以别把闸门当成"读懂意图"的检查器，它只保证"有东西在"。

`prompt` 里只给了任务书路径时，闸门会去读那个任务书，找「上一份报告状态行原文」标题
（可带引用块、`#`、`**`、`（必填）/（逐字）` 后缀），再校验紧随其后的声明行。

**注意:闸门只校验「有依据」，不校验依据与被派角色的语义是否一致。**
它的作用是把「静默跳步」变成「显式声明」，不是替代你判断。

## 三条硬规矩

**① 模型路由靠配置，不靠提示词。**
换模型 = 改角色文件里的 `model:` 字段。在提示词里写「你是某某模型」没有任何机制作用，
只会误导后来读配置的人（包括你自己）。

**② 任务书给路径，不给内容。**
让子智能体自己读文件（它有便宜通道），任务书只写路径、参数、验收标准。
贴一大段内容进任务书，等于把贵的那一环也变贵。

**③ 产物落盘，只回摘要。**
证据、脚本、报告全写文件，返回只给摘要加路径。不然中间过程全挤回主会话，上下文很快就满。

再加一条审查专用的：

**④ 报告以状态行收尾。**
格式 `〔下一跳:<下一动作>(之后→<后续>;闭案条件=<…>)〕`。首跳 = 下一个必须派发的角色 + 环节。
这既是给下一环看的路标，也是闸门认的「进场依据」。

## 问题分级:按真实场景,不按看起来严不严

审查角色输出的每一级都要求可执行：

| 级别 | 判定 | 必须附 |
|---|---|---|
| **P0** | 真实使用路径上会导致错误 / 数据损坏 / 假绿 / 安全事故 | 触发场景、发生概率、影响、最小修复 |
| **P1** | 真实场景可达且影响明确；或低概率但严重、且最小修复是局部小改动 | 同上四要素，**缺一不得升 P1** |
| **P2** | 风格建议 / 优化建议 / 极端场景 | 注明「不建议为此做复杂设计」 |

极端场景（多重独立故障叠加、非真实路径、修复需新增复杂机制）默认 P2；
但如果影响是数据损坏 / 安全事故 / 对外交付错误，降级后要**单列**出来交人拍板，不能静默丢掉。

## 安装

完整步骤见 **[install.md](install.md)**。最短路径：

```bash
# 1. 角色文件
mkdir -p ~/.zcode/agents
cp agents/first-reviewer-a.md agents/first-reviewer-b.md ~/.zcode/agents/

# 2. hook 脚本
cp hooks/*.py ~/.zcode/agents/
chmod +x ~/.zcode/agents/*.py

# 3. 把 config-hooks.snippet.json 里的 hooks 段合并进 ~/.zcode/cli/config.json
# 4. 重开会话，然后在同一个会话里连派两次同一个审查角色，看日志
tail -5 ~/.zcode/agents/.review-rotation.log
```

改完角色定义要**新开会话**才生效（引擎每轮对话开始重读角色配置）。

### 自测

三个 hook 的行为都有回归测试，零依赖、不碰你的真实配置：

```bash
python3 test/smoke.py
```

它会覆盖：轮换交替、固定成员标记、显式前台不被覆盖、非审查角色零影响、
fail-open、闸门拒绝/放行、任务书路径式依据的六种真实写法、登记表写入、
自愈的修复与幂等。**30 项全绿才算装对了。**

## 怎么查自己的模型标识

角色文件里的 `model:` 填的是**你机器上**的模型标识，不同账号不一样。两种查法：

**最稳的**:在 ZCode 面板里给某个角色选一次模型，让它自己把 `model:` 行写出来，
抄下那个值，再手写回文件（面板保存会丢字段，只拿它当「取值器」用）。

**命令行**:

```bash
python3 - <<'EOF'
import json, os
p = os.path.expanduser('~/.zcode/v2/provider_config.json')
d = json.load(open(p))['config']
for r in d.get('providerConfigRules', {}).get('providerRules', []):
    pid = r.get('providerId')
    cfg = r.get('config') or {}
    for m in (cfg.get('modelOrder') or cfg.get('personalModelIds') or []):
        if pid:
            print(f'{pid}/{m}')
EOF
```

字段结构随版本可能变化；拿不到就回到面板取值那条路。

## 已知边界

诚实说几条：

- **这是一套需要养的基建，不是「配一次就完事」。** 改任何一处规则，都要同步角色定义、
  hook 里的常量、以及你的流程文档。如果你的活儿不多、模型池里也没有多个家族可选，
  建议不要上——**官方给的「几个模型搭配」能解决的事，别自己造厨房**。
- **只有一个模型池时这套不成立。** 「终审保证异构」的前提是你池子里真的有两个以上不同家族。
- **闸门是存在性校验，不是语义校验。** 诚心要绕，它拦不住；它拦的是无意中的漂移和模板复用。
- **长思考模型在审查位上更好，但也真的慢。** 放前台干等体验会差，所以轮换 hook 默认注入后台。
- **面板保存会丢字段。** 这是 `heal_frontmatter.py` 存在的原因；手写 markdown 文件才是完全体。

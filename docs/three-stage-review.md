# 三段式审查：从自审到异构终审

> 这份文档说明审查链的完整形状：每一环由谁做、交付什么、下一环凭什么开始。
> 角色定义在 [`agents/`](../agents/)，自动拦截在 [`hooks/`](../hooks/)，主会话的调度约定在仓库根 [`AGENTS.md`](../AGENTS.md)。
> 如果只想知道「怎么装」，看 [`install.md`](../install.md)；这里回答「为什么这样组织」。

## 0. 一句话版本

```
产出方 L0 自审 → L1 修复（产出方按自审结果修复） → L2a 独立一审 →（重量级）L2b 异构终审 → 收口
```

轻量产物在 L2a 结束；重量级产物必须走完 L2b。

## 1. 为什么产出方不能自己审

三个原因，按严重程度排：

1. **写作记忆。** 产出方知道自己为什么这样选，会把「当时的权衡」当成「现在的证据」。
2. **同源盲区。** 同一个模型觉得没问题的写法，往往正是它会写出来的写法。
3. **沉没成本。** 已经写了一版，再让它判「方向对不对」，它会倾向证明自己没白写。

审查不是再读一遍，是**换一双没有草稿记忆的眼睛**。

但一审也不保证异构：

- 一审有两名成员，轮换保证「两个独立视角」；但两个成员里通常有一个和主会话同家族
  （主会话用 DeepSeek 时，成员 B 也可能配成 DeepSeek）。
- 所以重量级产物需要 L2b：它的模型必须和产出方、一审都不同源。
- 一句话：**一审买独立性，终审买异构性。**

## 2. 角色

| 角色 | 位置 | 职责 | 不做什么 |
|---|---|---|---|
| 产出方（主会话 / `impl-worker`） | 上游 | 写方案、写码、做 L0、按报告修复 | 不给自己发「通过」 |
| `first-reviewer-a` / `first-reviewer-b` | L2a | 独立第一审；轻量产物审完即终审 | 不改被审文件；不替产出方辩护 |
| `reviewer` | L2b | 异构终审：方案、大 diff、测试报告 | 不接轻量产物；不替代一审 |
| 主会话 | 全程 | 判通道、做 L0、收单、修复、派下一环、对用户负责 | 不把裁决权下放 |

两个一审成员由 `review_role_rotation.py` 自动交替；记忆目录同源，经验对两位成员同时生效。
`reviewer` 是唯一一个「保证和上游都不同源」的角色，轻量产物不要派它。

## 3. 三档通道

| 通道 | 触发条件 | 审查链 | 终点 |
|---|---|---|---|
| **A 重量级** | 方案级、大 diff、进 repo、交付他人、定稿、自产方案与规范规则、无上游方案审的大改 | L0 + 一审 → 修复 → 修复审 → **L2b 全量终审** → 修复 → 一审 delta → 仅 P0/P1 修复触发 L2b 收口 | L2b 报告 0P0/0P1 |
| **B 豁免** | 上游当前实施版本已异构终审并闭案，且有版本锚（上游报告 + commit/版本） | L0 + 一审成员（`first-reviewer-a` / `-b`）规格对照审 | 一审即终审；准入 0P0/0P1 |
| **C 轻量** | 单文件小改、中小 diff、内部过程文档 | L0 + 一审 | 一审即终审；升格线 = P0 或 P1≥3 |

判定规则：

- **进 repo / 交付他人 / 定稿的判据优先于体量。** 一个 20 行的对外配置，也可能比 500 行的内部脚本更重。
- **存疑按重量级。** 判错的代价不对称：C 判成 A 只是多花一轮；A 判成 C 会把同源盲区放过去。
- **任务书必须声明通道判定和依据。** 审查员发现声明与事实不符时，以审查员判定为准，并在报告里标「通道争议（声明 X / 判定 Y）」。
- **B 通道链中任一轮新报 P0/P1，立即转 A。** 豁免只适用于「忠实实施已审方案」，不适用于新设计。
- **A 通道没有 L2b 报告，不得称「已 review」。** 一审通过不等于终审通过。

> 名称注意：**B 通道**指「豁免通道」，与一审成员 `first-reviewer-b` 是两回事。
> 前者是链长档位，后者是角色名。

## 4. L0 自审：派发前先证明自己是成品

L0 由产出方做，在写任务书之前完成。五项：

| # | 查什么 | 合格证据长什么样 |
|---|---|---|
| 1 | **同源一致性**：同一个事实在所有出现处一致（规则、模板、示例、角色文件） | `grep` 命中数与预期一致；列出每个落点；差异处已解释 |
| 2 | **状态真实性**：所有「已修 / 已验 / 通过」都有可复跑的证据 | 命令 + 输出 + 退出码；或文件行号 + 内容；不写「应该没问题」 |
| 3 | **引用有效性**：路径、行号、链接、命令目标都存在且语义匹配 | `test -e` / `rg` 结果；链接能打开；行号指向的内容与描述一致 |
| 4 | **动作可执行性**：每条要求都有执行主体、动作和判据 | 逐条列出「谁 / 做什么 / 怎么算完成」；没有「适当处理」这类空话 |
| 5 | **新旧一致**：旧表述已删除或明确标废，没有两套说法并存 | 旧文案 `grep` 为 0；确需保留的已标「已废弃」并指向新规则 |

**自查声明要逐项举证：动作 + 对象 + 数字或命令 + 结论。只打勾不举证 = 假绿。**

L0 不是形式。它决定一审看到的是成品还是草稿；草稿审出来的问题，大部分本该在 L0 就被自己发现。

## 5. 任务书：给路径，不给内容

最小模板：

```markdown
# 审查任务书：<被审产物名>

## 通道判定
<A/B/C>（依据：<判据>；不是 <另一档>，因为 <原因>）

## 上一份报告状态行原文
首审（链中第一环，无上一状态行）。

## 被审范围
<绝对路径 / diff 范围 / 明确不审的部分>

## 整体判断要求
方案类：报告第一节先复述目标与真实场景，判「成立 / 成立但有更优路径 / 方向不成立」；
后两者给 ≤2 候选（保留约束 / 真实场景收益 / failure mode / 迁移成本）或最接近替代与否决理由。
代码 diff、B 通道规格对照、测试报告：写 n/a 及原因；其中只有代码 diff 在「无上游方案审的大改」时例外，仍须给整体判断。

## 必查项
1. …
2. …
3. …

## 报告落盘
<绝对路径，本轮开工时该文件不存在>

## 审查任务
<审什么、审到什么程度、哪些不在范围>
```

写任务书的四条规矩：

1. **给路径，不给内容。** 让审查的人自己读文件；路径写绝对路径（或 `~` 开头）、不含空格。
2. **只补它拿不到的知识。** 业务前提、红线、验收口径；后台审查必须自包含，没有人回答追问。
3. **指定产物落盘目录。** 报告路径不要落在被审产物下面；repo 内只允许新建本轮报告文件，不改既有文件。
4. **超过约 80 行先写成 md 文件。** 同一角色多开或共享记忆目录时，声明「本轮不写 memory」，新发现只进返回报告。

必查项写 3-6 条，每条都能用「是/否 + 证据」回答。范围外的发现可以作 P2 备注，不阻塞闭案。

## 6. 报告契约

报告固定结构：

```markdown
# <产物名> · <环节> 审查报告

> 审查员 / 审查时刻 / 被审范围 / 通道判定 / 进场依据 / 本轮是否写记忆

## 0. 整体判断
- 目标复述 / 真实场景 / 成立性（`- 成立性:成立` / `- 成立性:成立但有更优路径` / `- 成立性:方向不成立`）
- 若「更优」或「方向不成立」：候选 ≤2 或最接近替代与否决理由；检查范围
- 若不适用：`n/a` 及原因

## 1. 结论
P0×N / P1×N / P2×N，一句话说清能不能往下走。

## 2. 必查项逐项结论
| 必查项 | 一句话结论 |
|---|---|
| … | … |

## 3. 问题清单
### P0-1（阻塞）<一句话标题>
- 触发场景：…
- 发生概率：…
- 影响：…
- 最小修复：…
- 证据：<文件:行 / 命令 / 输出位置>

## 4. 未能验证的点

## 5. 修复执行要求（给主会话）
<可执行指令清单：改哪里、怎么验、哪些不做>

〔下一跳:…〕
```

几条硬约束：

- **整体判断是报告第一节，先于问题清单。** 先读问题清单再谈方案，注意力已经被原方案锚定；没有固定落点，「整体想想」一定会被跳过。
- **不新增严重度。** 方向不成立按四要素落 P0/P1；更优但非必须记 P2；结构性换方案记待拍板。不要发明「P0.5」「方向级」。
- **P0/P1 四要素缺一不可。** 触发场景、发生概率、影响、最小修复。缺一项就降级，不能靠语气升格。
- **「未能验证」要如实写。** 没读到、没跑通、无法验证的，逐条列出来；不猜。
- **报告写盘，返回只给摘要 + 路径。** 结论只留在返回消息里，下一环接不上。
- **状态行是最后一行。** 后面不要再写「以上」之类的尾巴。

`n/a` 的边界：

- 整体判断适用于方案 / 设计 / 规范 / 机制类产物。
- **代码 diff、B 通道的规格对照、测试报告**不要求整体判断，写 `n/a` 及原因。
- **只有代码 diff 在「无上游方案审的大改」时例外**，仍须给整体判断。
  不要把例外扩大到 B 通道或测试报告。

## 7. 状态行：把「下一跳」变成义务

格式：

```
〔下一跳:<下一动作>(之后→<后续>;闭案条件=<…>)〕
```

- **首跳 = 下一个必须派发的角色 + 环节。** 它不是建议，是义务；下一次派发必须与它一致。
- **修复审是新派发，不是 resume。** 主会话修复后按状态行派一审角色；resume 只用于同一审查员对同一轮报告的追问/补充（例如 C 通道 1-2 个 P1 的 delta 复核）。
- **中间必派环节不得折进闭案条件。** 修复审、复核是路，不是终点。
- **方案方向争议时首跳 = 用户裁决。** 审查员可以判定方向不成立，但不能替用户决定改不改。
- **结构性换方案记待拍板，不产生首跳。** 但主会话必须向用户显式列出，不能静默搁置。

例子：

```
〔下一跳:修复审(主会话修复本轮发现后派 first-reviewer-a;之后→reviewer 做 L2b 全量终审;闭案条件=L2b 报告 0P0/0P1)〕
〔下一跳:终审(派 reviewer 做 L2b;之后→修复 delta;闭案条件=L2b 报告 0P0/0P1)〕
〔下一跳:用户裁决(方案方向不成立;之后→按用户决定重做或放弃;闭案条件=用户书面结论)〕
〔下一跳:闭案(本轮 0P0/0P1; C 通道)〕
```

示例里的 `first-reviewer-a` 是岗位占位，实际成员由轮换 hook 决定；任务书不要写死成员名。

进场依据：

- 下一轮任务书必须**逐字**带上一份报告的状态行原文；首审写「首审（链中第一环，无上一状态行）」。
- 闸门 `review_dispatch_guard.py` 只校验「有没有依据」，不校验依据与被派角色是否语义一致。
- **静默跳过必派项 = 事故。** 不是「这次先这样」，是要在修复记录里记录的流程失效。

报告状态与 open 判定：

| 状态 | 含义 | P0/P1 是否仍 open |
|---|---|---|
| 已改待验 | 改了，但原失败场景还没复跑 | 是 |
| 已验待复核 | 原场景过了，但复核还没做 | 是 |
| 已闭 | 复核通过，状态行指向闭案 | 否 |

主会话不得自判已闭；「已修复」「已落地」「已闭环」都要有证据。

## 8. 修复闭环：从收到报告到下一跳

顺序不要跳：

1. **完整收单。** 先读完整份报告，首读前不改产物。不要看到第一个 P0 就开工，后面可能有根因相同的条目。
2. **逐项处置 + 根因聚类。** 能合并的同类问题一次修；不为每条打一个补丁。
3. **双轴影响面。** 运行时消费点（谁在读这个字段/文件）× 语义消费方（谁依赖这个结论/规则）。只改定义不改消费方，是最常见的假修复。
4. **原失败场景验收。** 先复现原来的失败，再证明现在通过；只跑新测试不算。
5. **合并态一次自审。** 单项修复都过，合在一起可能冲突；全部改完后按合并态再走一遍。
6. **L0-delta。** 只重查改动面及其消费方，不做全量二轮；但同源一致性、新旧一致这两项要覆盖到所有落点。
7. **按状态行派下一环。** 报告说修复审就派修复审，说终审就派终审；改道要有书面理由。

修复记录：

- 一条审查链只维护一份 Markdown 清单，不另起第二份；它就是给下一环看的处置记录。
- 每条写清：来源（哪份报告哪个编号）、处置（修复 / 不处置 / 待拍板）、落点、原失败场景验收、状态。
- 不处置的 P2 要写理由，不能静默消失。

## 9. 分级与轮数上限

**分级按真实场景，不按看起来严不严。**

| 级别 | 判定 | 必须附 |
|---|---|---|
| P0 | 真实使用路径上会导致错误 / 数据损坏 / 假绿 / 安全事故 | 四要素 |
| P1 | 真实场景可达且影响明确；或低概率但严重、且最小修复是局部小改动 | 四要素，缺一不得升 P1 |
| P2 | 风格建议 / 优化建议 / 极端场景 | 注明「不建议为此做复杂设计」 |

- 极端场景（多重独立故障叠加、非真实路径、修复需新增复杂机制）默认 P2。
- 如果极端场景的影响是数据损坏 / 安全事故 / 对外交付错误，降级后要**单列**出来交用户拍板，不能静默丢掉。
- **修复审 ≤5 轮。** 超过就停，交用户或重做方案；不要用无限加轮掩盖方向问题。
- P2 不阻塞闭案；但 P2 里的高危项要单列。

## 10. 两个最小例子

**C 通道：改一个内部文档的错别字**

```
L0 五项 → 派 first-reviewer-a（任务书写「首审」）
→ 报告 0P0/0P1，状态行 〔下一跳:闭案…〕
→ 结束
```

C 通道若报 1-2 个 P1（未到升格线）：修复后 resume 原审查员做 delta 复核（同一轮追问/补充），不升 A、不派 L2b。

**A 通道：给仓库加一个跨 3 个文件的配置项，并写规范说明**

```
判 A（进 repo + 规范规则）
→ L0 + 任务书
→ first-reviewer-a 一审（0P0/1P1）
→ 主会话按报告修复 → 派修复审
→ 修复审 0P0/0P1，状态行指向 L2b
→ reviewer 做 L2b 全量终审
→ 有 P0/P1 则修复 + 一审 delta + L2b 收口；没有则闭案
→ 没有 L2b 报告，不得称「已 review」
```

## 11. 常见误用

1. **一审过了就发。** A 通道的一审只保证「两个独立视角」，不保证异构。
2. **把 reviewer 的建议当指令。** 审查员的修复建议是线索，不是圣旨；照着改之前先验证它是否真的成立。
3. **状态行写「已修复」但没有证据。** 状态行不是愿望，是交接单。
4. **任务书贴大段内容。** 把贵的那一环也变贵，还挤掉审查员的独立阅读。
5. **跳过 L0，直接派审。** 让审查员替你找错别字和断链，浪费的是异构视角。
6. **把闸门当语义检查器。** 它只保证「有东西在」，不保证「东西对」。
7. **报告不落盘。** 结论只在返回消息里，下一环接不上，复盘也没有证据。
8. **同一轮的追问/补充重派新 agent。** 应该 resume 原实例；重派会丢掉它已经建立的上下文；修复审是跨修复轮的新派发，见 §7。
9. **多个并行实例同时写 memory。** 互相覆盖，最后谁的结论都不算数。
10. **只跑新测试，不复现原失败场景。** 新测试通过只证明新路径，不证明原来的坑填了。

## 12. hooks 与流程的边界

| 环节 | 自动 | 手工 |
|---|---|---|
| 一审成员交替、审查转后台 | `review_role_rotation.py` | 固定成员（`REVIEW-ROLE-FIXED`，仅当次） |
| 进场依据存在性 | `review_dispatch_guard.py` | 依据是否真实、是否对应正确环节 |
| frontmatter 补字段 | `heal_frontmatter.py` | 规则本身的维护 |
| 通道判定、L0、收单、修复、闭环 | — | 主会话 |

Hook 把「静默跳步」变成「显式声明」，**不替你判断声明是否成立**。

核心审查规则不变；如果你把链拉得更长，按同样的契约扩展即可。
